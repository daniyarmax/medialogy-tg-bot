## Phase 2 — Downloader (yt-dlp)

- **Status:** Complete
- **Date:** 2026-11-06
- **What works (verified):**
  - `app/downloader/platform_detector.py`: explicit host allowlist for YouTube/Instagram/TikTok/Facebook/X(Twitter)/Reddit, feeding `validate_source_url`'s `allowed_hosts`. 14 unit tests cover every platform's recognized domains plus rejection of unsupported hosts/malformed URLs.
  - `app/downloader/metadata.py`: `probe_metadata()` runs `yt-dlp -J --no-playlist` as a subprocess (JSON parse, no download), validating the URL first. 4 unit tests (mocked subprocess + mocked DNS) cover success parsing, unsupported-platform rejection, non-zero exit, and timeout (confirmed the process is actually killed on timeout).
  - `app/downloader/ytdlp_client.py`: `download()` runs the real yt-dlp download subprocess, disk-to-disk, with line-oriented progress parsing and `--continue` for resumability. 5 unit tests (mocked subprocess) cover progress streaming, oversized-file rejection, network timeout, SSRF-blocked URL (confirmed the subprocess is **never spawned** for a disallowed host), and missing-output-file detection.
  - **Real-network manual verification** (not mocked) against `https://www.youtube.com/watch?v=jNQXAC9IVRw` ("Me at the zoo", 19s — public, legally accessible, tiny):
    - `probe_metadata()` returned the correct title, platform, 19s duration, uploader, and 24 real formats.
    - `download()` fetched format `134` end-to-end: progress callback fired 10 times with percent climbing 0.3% → 100%, and the resulting file's size (322379 bytes) matched the probed `filesize_bytes` exactly.
  - **Two real bugs found and fixed via this live verification** (would not have been caught by mocked tests alone):
    1. yt-dlp silently suppresses all `--progress-template` output when stdout isn't a TTY (our subprocess pipe) unless `--progress` is also passed — zero progress lines were being emitted at all until this was added.
    2. `%(progress.total_bytes_estimate)s` is frequently `"NA"`; `%(progress.total_bytes)s` is now also requested and tried first.
  - Also upgraded the pinned `yt-dlp` from `2024.10.22` (originally spec'd) to `2026.10.26` after discovering the old version could no longer extract any YouTube formats at all — yt-dlp requires frequent updates to track upstream platform changes; **noted as an operational concern for Phase 7 deployment** (the worker image should pin a recent yt-dlp and this should be revisited periodically).
  - `pytest tests/unit tests/integration -v` → **39/39 passed**.
- **Known gaps:** None for this phase's scope. Format *selection* for multi-stream (video-only + audio-only) formats requiring an ffmpeg mux was not exercised locally (ffmpeg isn't installed outside Docker on this dev machine) — muxed-format download will be exercised once Phase 3 (ffmpeg) and the worker Docker image are in place.
- **Next phase prerequisites:** None blocking.

## Phase 3 — Audio/FFmpeg Engine

- **Status:** Complete
- **Date:** 2026-11-06
- **What works (verified):**
  - `app/processor/media_info.py`: `probe()` runs `ffprobe` as a subprocess and parses duration/audio-stream/video-presence/tags. Verified against 3 real checked-in fixtures (video+audio mp4, audio-only m4a, audio-only mp3) plus a missing-file error case.
  - `app/processor/ffmpeg.py`: shared subprocess runner parsing `-progress` key=value blocks into percent-complete updates, with timeout enforcement (SIGTERM, then SIGKILL after a 5s grace period).
  - `app/processor/audio_extractor.py`: `extract_audio()` for MP3/WAV/M4A/FLAC/OPUS. `needs_reencode()` is a pure function tested independently of ffmpeg (5 unit tests covering matching-codec/no-bitrate, bitrate-within-slack, real-downgrade, codec-mismatch, and lossless-format-ignores-bitrate cases).
  - Installed **ffmpeg 9.0.2 via Homebrew** specifically so this phase could be verified against the real binary rather than mocked (per the "no mocks standing in for production code" constraint — this is integration-adjacent logic that has to be proven to actually run). Confirmed `libmp3lame`, `libopus`, `aac`, `flac`, `pcm_s16le`/`pcm_s24le` encoders are all present.
  - Generated 3 tiny (37-76KB) checked-in test fixtures via `ffmpeg -f lavfi` (synthetic test pattern + sine tone), never downloaded real media: `sample_video.mp4` (3s, h264+aac), `sample_audio.m4a` (3s aac), `sample_audio.mp3` (3s mp3).
  - 15 tests in `tests/unit/test_media_info.py` + `test_audio_extractor.py` all run **real ffmpeg subprocess calls** (not mocked) and pass, covering: video-to-mp3 extraction (video stream stripped), the copy-path (m4a→m4a, verified lossless — identical bitrate and duration to the source, unlike a real transcode which would drift), flac/opus/wav conversion with correct resulting codec, OPUS's forced 48kHz resample, and progress callbacks firing with percent reaching ≥90%.
  - **Manual verification beyond the test suite:** ran `extract_audio()` by hand on the video fixture at 192kbps and independently cross-checked the output with a separate `ffprobe` invocation — confirmed `codec_name=mp3`, `bit_rate=192000`, `sample_rate=44100`, `duration=3.000000` exactly matching the request.
  - **Manual timeout verification:** ran `extract_audio()` with an artificially tiny `timeout_seconds=0.001` against the video fixture — confirmed `ProcessingTimeoutError` was raised quickly (0.06s, not hung) and `ps aux` showed **no orphaned ffmpeg process** afterward, proving the SIGTERM/SIGKILL escalation actually kills the subprocess rather than just raising while it keeps running in the background.
  - `pytest tests/unit tests/integration -v` → **55/55 passed**.
- **Known gaps:** None for this phase's scope.

## Phase 4 — Telegram Bot (aiogram 3)

- **Status:** Complete
- **Date:** 2026-11-07
- **What works (verified):**
  - `telegram_client.py`: Standard/Local Bot API abstraction (`build_bot()` + `TelegramLimits`). Validated against the real Telegram API (`bot.get_me()` confirmed the token resolves to `@medialogy_bot`).
  - `keyboards/`: main menu, quality picker (dedupes by resolution, picks `+bestaudio` for video-only formats), audio format/bitrate pickers. 10 unit tests.
  - `handlers/`: start/help, download (URL probe → quality picker → task admission), audio (URL or sent file → format/bitrate picker → task admission), status/cancel/my-downloads, settings. 8 unit tests for status/settings handlers (mocked repos).
  - `middlewares/`: DB session injection, Redis-backed rate limiting (4 integration tests against **real local Redis**), structlog context binding.
  - `services/task_service.py`: the shared admission-control + Task-creation gate. 3 integration tests against **real local Postgres** (creates pending task, rejects over the concurrency limit, allows a new task once an old one completes).
  - `progress_tracker.py`: pure throttle/render logic, 7 unit tests (no I/O).
  - **Full live verification against a real Telegram bot** (not mocked): got a real bot token from the user via @BotFather, validated it, ran the actual `python -m app.main` polling loop, and the user interacted with `@medialogy_bot` directly in Telegram.
    - Sent a real `youtu.be` link with tracking params → probed via real yt-dlp → quality keyboard shown → tapped a quality → confirmed via `psql` a real `tasks` row landed in Postgres: `operation=download_video`, `requested_format=243+bestaudio`, `status=Pending`, correct `source_url`/`platform`.
    - Used the Extract Audio flow on the same link → format picker (MP3) → bitrate picker (128kbps) → confirmed a second real `tasks` row: `operation=extract_audio`, `requested_format=mp3`, `requested_bitrate=128k`.
    - A real `users` row was created for the actual Telegram account that messaged the bot (telegram_user_id captured correctly).
  - **Two real bugs found and fixed via this live run** (neither would have been caught by unit tests alone, since they only manifest when wiring the whole app together):
    1. `main.py` had `settings = get_settings()` shadowing the imported `app.bot.handlers.settings` module — crashed on startup with `AttributeError: 'Settings' object has no attribute 'router'`. Fixed by aliasing the import (`from app.bot.handlers import settings as settings_handlers`).
    2. The download-URL handler only fired while FSM state was `DownloadFlow.waiting_for_url` — a user who pastes a link directly (without first tapping "Download Video") got silently ignored (`Update ... is not handled` in logs). Fixed by adding a `StateFilter(None)` fallback: a bare link in the default state is now treated the same as pressing the button first. Also hit and fixed a `FileNotFoundError: yt-dlp` when the bot process's `PATH` didn't include the venv's `bin/` — documented as a deployment note (the Docker worker image installs yt-dlp/ffmpeg system-wide so this won't recur there).
  - `pytest tests/unit tests/integration -v` → **88/88 passed**.
- **Known gaps:** `/settings`, `/help`, and "📁 My Downloads" were exercised only by unit tests with mocked repos, not live in Telegram during this session (the core flows — download and audio-extraction task creation — were the ones live-verified). Local Bot API Server mode (`TELEGRAM_API_MODE=local`) is implemented but untested — deferred to Phase 7, which requires the operator's own `my.telegram.org` credentials.
