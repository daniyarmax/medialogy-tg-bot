## Phase 1 — Core Infrastructure

- **Status:** Complete (with one noted gap — see below)
- **Date:** 2026-11-06
- **What works (verified):**
  - `app/core/config.py`: Pydantic Settings with nested telegram/database/redis/celery/storage/limits groups. Verified by actually loading from a real `.env` file (`get_settings()` returns correct nested values).
  - `app/core/logging.py`: structlog configured with console and JSON renderers, context binding (`task_id`/`user_id`). Verified by manually running both modes and inspecting the rendered output (console: colorized key=value; JSON: structured line with all bound fields).
  - `app/core/exceptions.py`: `MediaBotError` hierarchy with per-subclass `user_message`, covering all error categories from the plan.
  - `app/core/security.py`: SSRF-safe URL validator + filename sanitizer. Verified with 13 unit tests covering: non-http schemes, literal loopback/private/link-local IPs, known cloud-metadata hostnames, DNS-rebinding (hostname resolving only to a private IP, via mocked `socket.getaddrinfo`), a valid public URL, platform allowlist accept/reject, and filename sanitization edge cases. All pass (`pytest tests/unit/test_security.py -v`).
  - `app/database/models.py`, `repository.py`, `session.py`: SQLAlchemy async models for `users`/`tasks`/`download_history` plus partial indexes (`idx_tasks_user_active`, `idx_tasks_updated_at_active`) declared directly on the model so `alembic check` has nothing to drift on.
  - Alembic: initial migration autogenerated and hand-extended with the two partial indexes, then actually applied (`alembic upgrade head`) against a **real local Postgres 16** (via Homebrew, not Docker — see gap below). Verified: `\dt`/`\di` show all 3 tables + 11 indexes, `alembic check` reports "No new upgrade operations detected."
  - 4 integration tests (`tests/integration/test_repositories.py`) exercise `UserRepository`/`TaskRepository`/`DownloadHistoryRepository` against that real database — admission-control counting, status updates, and the history→task link all verified. `pytest tests/unit tests/integration -v` → **17/17 passed**.
  - Found and fixed a real bug during this verification: `run_async()` in `session.py` originally used `asyncio.run()` per call, which creates a fresh event loop every time — incompatible with the cached, pooled async engine (asyncpg binds connections to the loop that opened them). Fixed to reuse one persistent event loop per worker process. This matters for Phase 5 (Celery tasks will call through `run_async`).
  - `docker-compose.yml` (postgres+redis) and `docker/Dockerfile.{bot,worker}` written per the plan (two-image split, worker-only ffmpeg).
- **Known gaps:** Docker Desktop's CLI was unresponsive for this entire session (`docker ps`/`docker info` hang indefinitely even though the VM process is running) — `docker compose up postgres redis -d` has **not** been run/verified. All DB/migration work above was verified against a local Homebrew Postgres 16 + Redis 7 instead, which exercises the same SQL/schema but not the Compose file itself. **Follow-up:** once Docker Desktop is restarted and responsive, run `docker compose up postgres redis -d` and re-confirm healthy status before relying on this phase's Docker setup.
- **Next phase prerequisites:** None blocking — Phase 2 (downloader) has no dependency on Docker being verified.
